# CLOCK Release Process

CLOCK releases are deterministic build-and-publication jobs. A tagged release is not considered complete unless the complete firmware flavor matrix, user manual, licenses, notices, changelog, build provenance, and checksum manifests are present.

## Firmware flavor matrix

Every tagged release builds the same source revision five times. The compiled boot Easter egg is the only intended difference between the images.

| Flavor | Easter egg | Public filename |
| --- | --- | --- |
| `default` | BEATKNECHT | `eurorack-clock-firmware-default-<version>.dfu` |
| `pixel-raid` | Pixel Raid | `eurorack-clock-firmware-pixel-raid-<version>.dfu` |
| `formula-1` | Formula 1 | `eurorack-clock-firmware-formula-1-<version>.dfu` |
| `breakout` | Breakout | `eurorack-clock-firmware-breakout-<version>.dfu` |
| `egg-journey` | Egg Journey | `eurorack-clock-firmware-egg-journey-<version>.dfu` |

The `.dfu` images contain only the boot and application Flash regions. Persistence sectors are omitted deliberately so routine firmware updates do not erase CURRENT, presets, or score data.

## Required release payload

A release is rejected unless all of the following exist:

- all five versioned firmware `.dfu` files;
- `clock-user-manual.<version>.pdf`;
- `clock-user-manual.<version>.odt`;
- `CHANGELOG.md`;
- `RELEASE_SUMMARY.md` and generated `RELEASE_NOTES.md`;
- `LICENSE.md` and `NOTICE.txt`;
- `MANUAL-LICENSE.md`;
- `THIRD_PARTY_NOTICES.md`;
- BSD-3-Clause, Apache-2.0, and SDL/zlib license texts;
- `GNU-ARM-EMBEDDED-7.2.1-LICENSES.zip`, captured from the exact pinned PlatformIO toolchain package used for the build;
- `BUILD-INFO.txt`, derived from the linker map of every firmware flavor;
- `SHA256SUMS.txt` and `MD5SUMS.txt` over the complete published payload.

The native simulator is not a release artifact. A future VCV Rack package may be included when present, but it is not currently a release prerequisite.

## License and build provenance

The embedded target is pinned to `platformio/toolchain-gccarmnoneeabi@1.70201.0`. The release job verifies that the installed compiler identifies itself as GCC 7.2.1, then archives the license material from that exact package. This keeps the binary release tied to the toolchain that actually produced it rather than to a generic or newer license bundle.

Every release PlatformIO environment also emits `firmware.map`. `BUILD-INFO.txt` records the map hash and static archives referenced by each flavor. This provides an auditable bridge between the published binary and its runtime-license inventory.

## Manual publication

The frozen release manual lives at:

```text
docs/manual/releases/<version>/clock-user-manual.<version>.odt
```

The release workflow validates that ODT, builds both the versioned ODT and PDF with the required Ubuntu fonts, and validates the exported PDF before publication. The manual contains the firmware license, third-party license notices, and a QR code to the source repository before the Colophon.

Firmware-version stamping is deliberately scoped to firmware-bearing fields and prose. **License names and license versions are immutable release content**: for example, publishing firmware `1.1.0` must not alter `PolyForm Noncommercial License 1.0.0`, `CC BY-NC 4.0`, Apache-2.0, BSD-3-Clause, or any other third-party license identifier. The manual-tooling regression suite enforces this separation.

## Release description

GitHub release notes are generated from three curated sources rather than GitHub's generic automatic notes:

1. the frozen `RELEASE_SUMMARY.md` for the user-facing overview;
2. the firmware-flavor and documentation/license artifact description generated by `scripts/release_notes.py`;
3. the exact matching `CHANGELOG.md` section plus a source-compare link to the preceding version.

This follows the same principle used by the Quantizer release workflow: concise user-facing context first, detailed changes second, with reproducible artifacts and checksums attached.

## Tagging

For a normal release:

```bash
git tag v<version>
git push origin v<version>
```

The workflow validates that the tag matches `src/version.h`, runs all release gates, builds the five ARM images, creates the manual and legal payload, uploads the complete `dist/` directory as a workflow artifact, and only then creates the GitHub Release.
